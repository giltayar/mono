# @giltayar/nx-btp

## Repository-local Nx workflows (Carmbo)

This private package owns the Nx executor, version helper, workflow preset, build/lint configuration,
and tests. The monorepo consumes it through a repository-local executor path, not a published
dependency or package-manager link.

Nx is an orchestration tool, not a package-manager workspace. Each package keeps its
own dependencies, lockfile, configuration, and published package dependencies. Only the seven
packages under `packages/carmbo` are configured initially.

With Node.js >=26.9.0, install the root Nx host and this package independently from the repository root:

```sh
pnpm install
pnpm --dir packages/commons/nx-btp install
```

The [src/.pnpmfile.mjs](./src/.pnpmfile.mjs) hook approves Nx's installation script without creating
a workspace configuration file. The package-root `.pnpmfile.mjs` is a discovery shim; the monorepo's
root hook also re-exports the implementation for the root Nx installation. Other packages do not
inherit this configuration.
An installed global `nx` CLI uses this local installation; alternatively use `pnpm exec nx`.

### Configuration

The root `nx.json` extends this package's [nx-preset.json](./nx-preset.json). The preset defines
both targets as target defaults, and sets `"parallel": 1` so that tasks run one at a time,
avoiding concurrent pnpm self-updates and Git operations:

- `start-btp` runs the built-in `nx:run-commands` executor.
- `btp` (build-test-publish) runs this package's `./packages/commons/nx-btp:btp` executor and
  depends on the `btp` of the project's dependencies:

```json
"dependsOn": [{"target": "btp", "dependencies": true, "params": "forward"}]
```

This is `^btp` with `"params": "forward"`, so CLI options such as `--msg` and `--dry-run` reach
the dependencies' `btp` too. Plain `"^btp"` would drop them: a dry run would really publish
changed dependencies.

Target defaults only configure targets that a project declares; they cannot add targets. So each
package opts in with a `project.json` that names the project and declares the two targets, empty:

```json
{"name": "carmbo-pages-auth", "targets": {"start-btp": {}, "btp": {}}}
```

The `project.json` is also what makes Nx treat the package folder as a project, since there are no
package-manager workspaces.

Nx infers dependencies from each package's `package.json`. It links two projects only while the
dependency's local version satisfies the dependent's version range. That's why internal
dependencies use caret ranges (`"@giltayar/carmbo-commons": "^2.3.0"`): after `carmbo-commons`
releases 2.3.1, the range still matches and the edge remains. With an exact pin (`"2.3.0"`), the
edge would disappear until the dependents update the pin.

The root keeps repository-wide discovery and analytics configuration.

[executors.json](./executors.json) loads [src/publish.ts](./src/publish.ts) directly using Node's
native TypeScript support. Running Nx workflows does not require building this package first.
The package's `dist` output is generated by its independent build.

### Start work (`start-btp`)

From the repository root:

```sh
nx start-btp carmbo-pages-auth
```

Runs `pnpm self-update`, then `pnpm update --latest`, in that package. Both targets are uncached.

### Build, test, and publish (`btp`)

**This command really publishes the package, commits it, and pushes to Git. Only run it when
you intend to release.** Commit the initial root Nx tooling separately before using this workflow.

```sh
nx btp carmbo-pages-auth --message='fix login redirect'
```

`btp` first runs `btp` for the project's dependencies (in dependency order, one at a time),
with the same options. Each dependency is released only if it changed, with its own commit
prefix and the same message. If a dependency fails, its dependents are not released.

The commit becomes `cpa: fix login redirect`. Prefixes are the initials of the hyphen-separated
folder name:

| Package                  | Prefix |
| ------------------------ | ------ |
| `carmbo-app`             | `ca`   |
| `carmbo-commons`         | `cc`   |
| `carmbo-pages-auth`      | `cpa`  |
| `carmbo-pages-community` | `cpc`  |
| `carmbo-pages-job`       | `cpj`  |
| `carmbo-pages-sale`      | `cps`  |
| `carmbo-pages-student`   | `cps`  |

Quote the message for your invoking shell. Once Nx receives it, the executor passes it literally
to Git, without shell interpolation. A non-empty `--message` (or its alias `--msg`) is required:

```sh
nx btp carmbo-pages-auth --msg='fix login redirect'
```

To check whether a package would be published, and as which version, without changing anything,
use `--dry-run`. The message is optional in a dry run; if given, the report includes the commit:

```sh
nx btp carmbo-pages-auth --dry-run
nx btp carmbo-pages-auth --dry-run --msg='fix login redirect'
```

A dry run performs the same checks as a real publish (staged changes, the registry lookup, and
change detection) and fails when a real publish would abort. It does not bump the version, build,
test, publish, commit, tag, or push.

With `CI=1` and `FORCE_COLOR=1`, the executor runs, in order:

1. Check whether the package changed since its last release (see
   [Change detection](#change-detection)). If the local version is published and nothing changed,
   it stops here successfully, without building, testing, publishing, or committing.
2. Select the next package version.
3. `pnpm update`: updates dependencies to their newest versions within their ranges (not
   `--latest`), then installs.
4. `pnpm --if-present build`
5. `pnpm --if-present test`
6. `pnpm publish --no-git-checks`
7. Stage only the current package.
8. Commit with the prefix and a Copilot co-author trailer.
9. Create the annotated release tag `<package-folder>@<version>` (e.g. `carmbo-pages-auth@1.0.4`)
   on that commit.
10. `git push --follow-tags`, which pushes the commit and its release tag.

Existing pnpm lifecycle hooks still run, including the Carmbo app's Docker hooks.
Set `NO_TESTS` to skip step 5; presence is enough, even an empty value:

```sh
NO_TESTS= nx btp carmbo-pages-auth --message='release validated changes'
```

Unrelated staged changes cause an error before version changes or publication. Staging is checked
again before the package commit. Unstaged changes elsewhere are neither staged nor committed.
Every failed command stops the workflow. A successful publication cannot be undone automatically
if a later commit, tag, or push fails. If tagging fails because the tag already exists locally,
delete the stale tag and push the commit and tag manually.

### Change detection

[src/package-changes.ts](./src/package-changes.ts) decides whether a published package changed,
using Git only, without building:

1. If the local `package.json` version is not published, the package needs publishing.
2. Otherwise, find the commit that was released as that version:
   - The release tag `<package-folder>@<version>`, when it exists, is authoritative.
   - Otherwise, search the history of the package's `package.json`: the release commit is the
     oldest of the consecutive most recent commits that still have the local version.
   - If neither is found, the package is treated as changed.
3. Compare the package folder with the release commit: modified, deleted, and new untracked files
   count as changes. Files ignored by `.gitignore` (such as `dist` and `node_modules`) never count.
4. Drop files matching the package's `btp.exclude` globs, and `package.json` changes that only
   touch the `btp` field.

Declare files that do not affect the published package in each package's `package.json`. Globs are
relative to the package folder, and `*` does not match dot files, so list them explicitly:

```json
"btp": {
  "exclude": ["test/**", "AGENTS.md", "project.json", "eslint.config.mjs", ".prettierrc"]
}
```

Keep build inputs, such as `tsconfig*.json`, `pnpm-lock.yaml`, and `pnpm-workspace.yaml`, out of
the exclusions so that changes to them still trigger a release.

The history search does not follow folder renames, so it stops at a commit that moved the
package. Release tags are not affected by later moves. The history search also trusts that the
release commit matches what was published; publishing only through this executor keeps them
consistent.

Check packages without publishing, from the repository root:

```sh
node packages/commons/nx-btp/src/package-changes.ts packages/carmbo/*/
```

It prints whether each package is unchanged since its release tag or commit, or needs publishing.

### Version selection

[src/next-package-version.ts](./src/next-package-version.ts) reads the current directory's `package.json` and queries
`npm info <name> versions --json`. It uses `publishConfig.registry` when present; otherwise npm
uses the package-local/scoped registry configuration. Registry credentials come from npm's
normal configuration.

An unpublished local version stays unchanged. If the version already exists, the script
increments the patch repeatedly until it finds an unused version. Only stable `major.minor.patch`
local versions are supported. Registry lookup failures, including package-not-found, fail explicitly;
publish a brand-new package manually first.

You can run version selection separately from a package directory:

```sh
node ../../commons/nx-btp/src/next-package-version.ts
```

`btp` releases changed dependencies before their dependents. When a dependent is released too,
its `pnpm update` step moves it to the newest dependency versions within its ranges, including the
ones just released, in its lockfile and in its `package.json` ranges' lower bounds. A dependent
that is unchanged is not updated or released: its consumers already get the new dependency
versions through its caret ranges.

pnpm ignores versions younger than `minimumReleaseAge`, which would hide a dependency released
moments earlier. Packages that set it must also set `minimumReleaseAgeExclude: ['@giltayar/*']`
in their `pnpm-workspace.yaml`, as the Carmbo packages do.

### Validate the tooling

From this package directory:

```sh
pnpm build
pnpm test
```

The repository root's `pnpm build` and `pnpm test` forward to these package-local scripts.
From the repository root, inspect configured projects with `nx show projects` or
`nx show project carmbo-pages-auth --json`.

`pnpm test` runs two kinds of tests:

- **End-to-end scenarios** (`pnpm test:e2e`, [test/e2e](./test/e2e)) run the real `nx btp`
  against a fake monorepo. Each scenario gets its own temporary Git repository with a bare
  `origin`, a private [Verdaccio](https://verdaccio.org/) registry, and small fake packages
  (`carmbo-alpha`, `carmbo-beta`) whose version 1.0.0 is already published. Scenarios then change
  files and assert what actually happened in the registry, the commits, and the tags on `origin`.
  They run concurrently, in a few seconds.
- **Unit tests** (`pnpm test:node`, [test/unit](./test/unit)) cover edge cases that are hard to
  produce for real, such as a command failing at each step, malformed registry output, invalid
  `btp` configuration, and `start-btp`.

The end-to-end scenarios are isolated from your environment: they use a temporary `HOME`, npm
configuration, and Git configuration, route only the `@fixture` scope to the local Verdaccio, and
push only to the temporary `origin`. They never publish to a real registry or touch this
repository.
